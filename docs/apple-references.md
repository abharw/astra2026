# Apple runtime references

2026-09-08 · Primary-source study for the proposed `SpatialApple` runtime. The current Swift/TypeScript slices are uncommitted; the owners below describe intended boundaries, and source observations are called out as such. Sources are Apple documentation and Apple sample archives inspected on 2026-09-08. Sample licenses were retained in the temporary download directories and no sample code was copied into this repository.

## Authored assets: preserve the hierarchy

Apple’s [entity-loading guide](https://developer.apple.com/documentation/realitykit/loading-entities-from-a-file) states that `Entity.load` / `Entity(named:)` returns the root and preserves descendants, while `loadModel` flattens a USD hierarchy into one `ModelEntity`. `loadAnchor` is for Reality files only. The guide also warns that synchronous loading blocks the calling actor; the async entity initializer is the app-safe path.

**Invariant for `SpatialApple`’s asset loader:** use asynchronous `Entity(named:in:)` or `Entity(contentsOf:withName:)` for an authored rack, retain the returned descendant tree, and map semantic `nodeId`s to descendant entities. Do not use `loadModel` when parts must remain independently selectable or editable. Keep root placement separate from local part transforms. This directly supports `docs/architecture.md`’s authored/generated common node model. The main rack now loads the approved Akeil USDZ through `Entity(contentsOf:)`; the earlier JSON recipe assembly remains available separately. Actual native import tests preserve 18 server bindings, with 149 entities and 55 models; the simulator also renders the source asset. See [import evidence](evidence/imported-rack-native.json) and [current API references](realitykit-import-references.md).

## RealityKit entities, components, transforms, and materials

The [Entity reference](https://developer.apple.com/documentation/realitykit/entity) says every entity has a component collection with at most one component of each type; `Transform` is relative to the parent. Apple’s [transform article](https://developer.apple.com/documentation/visionos/understanding-transforms) describes the tree as local transforms composed through containers. [`ModelComponent`](https://developer.apple.com/documentation/realitykit/modelcomponent) carries one mesh plus its material array, and [`Material`](https://developer.apple.com/documentation/realitykit/material) distinguishes physically based and unlit materials.

**Owner:** `SpatialApple` entity mapper/controller; `SpatialCore` stores only value-level transforms/material descriptions. A scene operation addresses a stable semantic ID, then the mapper finds the entity and updates its component/transform. The RealityKit tree is a presentation of accepted state, not the authority. For selectable generated parts, attach a `CollisionComponent` and use a deliberate picking proxy when visual geometry is too thin; the collision proxy must map back to the same semantic ID. Material edits should replace the `ModelComponent` material binding while reusing the mesh resource.

The Apple [dynamic-geometry sample](https://developer.apple.com/documentation/realitykit/generating-interactive-geometry-with-realitykit) (`HeightMapMeshEntity.swift`) makes this concrete: it sets `ComputeSystemComponent`, `ModelComponent`, `InputTargetComponent`, and `CollisionComponent` on one entity. Its source separates an editable mesh’s broad culling bounds from a preview mesh’s tight bounds. This is a useful pattern, but the sample is macOS 15/visionOS 2 and Xcode 16; its gesture and compute setup is not evidence that the iPhone/iPad app is implemented.

## Procedural meshes and actor isolation

For bounded generated geometry, Apple’s [`MeshDescriptor`](https://developer.apple.com/documentation/realitykit/meshdescriptor) example sets positions and triangle primitives, then calls [`MeshResource.generate(from:)`](https://developer.apple.com/documentation/realitykit/meshresource) and installs the result in `ModelComponent`. The current `MeshResource` and `LowLevelMesh` declarations are `@MainActor`. Apple’s [low-level mesh guide](https://developer.apple.com/documentation/realitykit/creating-a-plane-with-low-level-mesh) also says bounds are used for culling and must contain every possible vertex.

**Implementation rule:** normalize, validate, count, and calculate immutable vertex/index arrays in pure `SpatialCore`/compiler code; perform `MeshResource` creation, entity component mutation, and installation in the serialized `SpatialApple` main-actor commit. `async` does not prove background execution. Start with `MeshDescriptor` and switch to `LowLevelMesh` only for measured frequent deformation or a custom vertex layout. The official dynamic sample’s `PlaneMesh.swift` is explicitly `@MainActor`, computes exact capacities, fills buffers, and passes a `maxVertexDepth` into bounds; its `ComputeSystem.swift` dispatches one command buffer per frame. A generated model should not inherit that 512×512 dynamic workload merely because the API exists.

**Current source observation:** `framework/Sources/SpatialApple/Rendering/GeometryCompiler.swift` is `@MainActor`, caches by geometry/content hash, validates non-empty data, and uses `MeshDescriptor` for custom triangles. It does not yet expose explicit low-level culling bounds; deformation/culling behavior therefore remains a target-hardware check.

## Screen points, camera frames, and physical placement

`ARView` exposes [`raycast(from:allowing:alignment:)`](https://developer.apple.com/documentation/realitykit/arview/makeraycastquery%28from%3Aallowing%3Aalignment%3A%29), `trackedRaycast`, `entity(at:)`, `ray(through:)`, and `project`. `ARRaycastQuery` is a ray through a view point; an `ARRaycastResult` returns a world transform. [`ARFrame`](https://developer.apple.com/documentation/arkit/arframe) owns the camera, timestamp, captured `CVPixelBuffer`, and session raycast entry point. The current SDK spelling is `displayTransform(for:viewportSize:)`; Apple’s public/beta reference documents the equivalent [`displayTransform(viewRotationAngle:viewportSize:)`](https://developer.apple.com/documentation/arkit/arframe/displaytransform%28viewrotationangle%3Aviewportsize%3A%29), which maps normalized camera-image points to normalized view points while handling rotation and aspect-fill.

**Owners:** `SpatialApple`’s AR surface owns session configuration and placement; its pointing adapter owns image-to-viewport conversion; the app owns permission UX. For the required screen-aligned pointer, carry frame timestamp and orientation/viewport identity, apply the current display transform, reject stale observations, then call the RealityKit screen-point hit test and resolve the entity to `nodeId`. A physical placement flow can use `.estimatedPlane` for initial feedback and a tracked raycast while the surface estimate refines. Stop tracked raycasts when no longer needed.

The Apple [placement sample](https://developer.apple.com/documentation/arkit/placing-objects-and-handling-3d-interaction) is source-visible in `ViewController+ObjectSelection.swift`, `VirtualObjectInteraction.swift`, and `VirtualObjectARView.swift` (download: [`PlacingObjectsAndHandling3DInteraction.zip`](https://developer.apple.com/tutorials/d738f9c9c7fe/PlacingObjectsAndHandling3DInteraction.zip), Apple commit `17d69f656723726c06fcede0e7126f455342bae0`): one-time raycasts are used while dragging, tracked raycasts refine placement, and a bounding-box hit test provides forgiving selection. The archive still uses deprecated SceneKit/`ARSCNView`; transfer the interaction invariants to `ARView`, not the old class names.

**Current source observation:** `PointingNativeAdapters.swift` takes an existing `ARFrame`, applies `displayTransform(for:viewportSize:)`, and forwards `capturedImage` plus the frame timestamp to Vision while rejecting stale viewport generations. `ARViewFactory.swift` selects `.ar` on a physical iOS target and `.nonAR` for simulator mode; `NativeARView.swift` owns that selection. This is source wiring, not evidence of camera tracking or physical placement.

## Vision hand pose: landmarks are 2D input

Apple’s [Vision request reference](https://developer.apple.com/documentation/vision/vndetecthumanhandposerequest) returns `VNHumanHandPoseObservation` points with confidence. The official [Detecting Hand Poses with Vision](https://developer.apple.com/documentation/vision/detecting-hand-poses-with-vision) sample (iOS/iPadOS 14+, Xcode 12; download [`DetectingHandPosesWithVision.zip`](https://developer.apple.com/tutorials/063d51b92f5a/DetectingHandPosesWithVision.zip), Apple commit `ec30ff646e0c4b2a22c7867f94fe90fb73f98110`) uses an interactive capture queue, `VNImageRequestHandler(cmSampleBuffer:)`, one hand, confidence > 0.3, and converts Vision’s normalized y coordinate with `1 - y`. It then dispatches UI updates to the main queue. `HandGestureProcessor.swift` requires three consecutive observations before changing pinch/apart state.

**Owner:** `SpatialApple` pointing adapter. Reuse the existing AR camera/session frame source rather than opening a competing capture session. Keep detector output, smoothing, and cursor state separate from scene authority; a lost/low-confidence hand hides hover and does not mutate the scene. The sample’s thresholds are examples, not accepted Astra thresholds. The sample is front-camera drawing code, so rear-camera landscape orientation, ARView aspect-fill, and iPad ergonomics remain unverified. Two-dimensional landmarks do not establish a finger’s 3D direction.

**Current source observation:** `VisionHandPointDetector.swift` uses one `VNDetectHumanHandPoseRequest`, a default confidence of `0.55`, monotonic timestamps, and a single latest-pending-frame queue. That coalescing behavior is a deliberate runtime choice; it differs from the sample’s `0.3` confidence and three-observation pinch state machine and still needs device measurement.

## Simulator boundary

Apple’s placement sample explicitly says “ARKit is not available in iOS Simulator.” RealityKit’s [`ARView.CameraMode.nonAR`](https://developer.apple.com/documentation/realitykit/arview/cameramode-swift.enum/nonar) is a fully virtual environment using a virtual camera; `.ar` requires a device camera. Therefore simulator/non-AR runs can prove scene compilation, layout, deterministic hit tests, and accessibility, but cannot prove ARKit tracking, camera capture, physical placement, or hand pointing. `docs/testing-harness.md`’s evidence labels match this boundary. No camera-to-simulator bridge has been verified.

## Audio interruption and engine reconfiguration

Apple’s [audio interruption guide](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions) says observe `AVAudioSession.interruptionNotification`, inspect `.began`/`.ended`, and resume only when the ended notification contains `.shouldResume`. [`AVAudioEngineConfigurationChange`](https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/avaudioengineconfigurationchange) is separate: hardware sample-rate/channel changes stop and uninitialize the engine; nodes remain attached with old formats, and the app must reconnect as needed. Apple warns not to deallocate the engine inside that notification handler. [`AVAudioEngine`](https://developer.apple.com/documentation/avfaudio/avaudioengine) requires an explicit graph, `start()`, and `isRunning` checks.

**Owner:** app composition root’s native audio/session component, with the selected Realtime transport adapter. On interruption, pause/cancel local playback state and prevent stale narration from claiming current scene state; on ended/configuration change, reactivate, re-query route/format, reconnect if needed, and restart only when policy permits. The older Apple `AVAEGamingExample` source was not used as a primary current design because it is a 2016-era sample; the current notification contracts above are the evidence.

**Current source observation:** `app/AR/SpatialDemo/Conversation/AudioIOController.swift` is `@MainActor`, owns an engine/player graph, installs an input tap, and handles interruption, route-change, and media-services-reset notifications. It cuts playback on interruption and resumes only with `.shouldResume`. The first review found a missing `AVAudioEngineConfigurationChange` handler. It is now registered and rebuilds the graph; the handler extracts scalar notification values before crossing the actor boundary. Physical route/format-change recovery still needs a device test.

## What remains to verify on target hardware

The docs and samples establish API semantics and boundaries. They do not establish Astra’s frame latency, mesh-install hitching, ARView selection accuracy after display transforms, rear-camera hand-pose reliability, audio continuity during Realtime interruptions, iPad Air M4 ergonomics, or physical relocalization. Those require receipts and screen/frame evidence from the actual iPad/iPhone builds, with simulator and Mac-harness results labeled by their source mode.

Automatic foreground hand sampling forwards frames from the existing AR session into the Vision adapter and shared resolver. The physical iPad trial exposed a completed-result starvation bug when newer camera frames arrived during inference. Completed results now deliver monotonically, with viewport fencing and a regression test. An earlier iPad observation reported fingertip tracking and green target feedback; acceptance of the updated composer and automatic hand path remains pending. Combined pointing/voice and orientation accuracy remain unmeasured. The [focused hand-tracking source study](hand-tracking-references.md) records usable iOS examples and distinguishes incompatible visionOS hand APIs.
