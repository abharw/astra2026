# Asset and agent pipeline audit

2026-09-08. Source audit of the working tree before the current optimization pass. Findings below describe that baseline; an assigned fix is not a verified result. This review read the repository architecture, asset, format, storage, service, input, testing and evidence documents alongside the native and backend implementation. Apple and OpenAI references were checked for the relevant APIs; this is not a claim to have read every Apple document.

The existing separation is sound: **Blender/USD contains authored geometry, semantic JSON identifies editable assemblies, Astra proposes changes, and RealityKit renders the accepted result locally.** The main missing capability is choosing and loading a useful level of detail while preserving the identity of the assembly already being discussed. A new serialization format or rendering engine does not solve that by itself.

## Representation and tool decisions

Keep two linked data sets, rather than converting all CAD triangles into model text:

1. **Authored artifact:** immutable USDZ/Reality files plus source/export hashes, units, bounds, material information and validated part bindings. Blender and OpenUSD perform preparation before the interaction. The app downloads or loads a known package; the model never supplies a file path or arbitrary asset URL.
2. **Accepted semantic scene:** stable instance IDs, containment, current transforms, named roles, provenance and references into those artifacts. Add a small assembly catalog with rest poses and available detail levels. Send Astra the useful semantic view; keep the complete source-object index available for targeted inspection, outside the normal prompt.

Semantic granularity and visual LOD are different decisions. Astra chooses whether the explanation needs a rack, whole servers, cooling/memory/compute systems, or one part. The runtime chooses an affordable visual variant for that same semantic identity. Changing a visual variant must not change which server “this one” refers to. There is no need to instantiate or describe every screw to explain airflow.

The model-facing vocabulary should express bounded intent using observed IDs: translation of an explicit set, arrangement at an explicit assembly level, or requesting a known detail level. The normalizer performs arithmetic and expands the chosen set into ordinary absolute scene edits. Keep the strict reducer/hash/epoch contract; do not make Astra repeat quaternions and opaque hashes merely to move several servers. Destructive or recursive depth should be explicit. A request for all rack units must not implicitly mean every descendant.

The live path remains one Realtime conversation and an Astra scene author. OpenAI documents the function-call arguments → application execution → matching `function_call_output` → final response sequence. That sequence gives the application a place to provide accepted scene results; it does not automatically share Realtime conversation history with a separate Responses request. [Realtime function calling](https://developers.openai.com/api/docs/guides/realtime-conversations#function-calling).

## Asset performance decisions supported by sources

Preserve programmatic access at teaching-assembly boundaries and merge decoration inside them. Apple documents hierarchy-preserving `Entity` loading and flattened model loading; the latter sacrifices descendant access. Its performance guidance recommends shared resources, simpler collision shapes, asynchronous loading and smaller asset packages. These support the current native route; they do not establish that a different SDK would be faster. [Entity loading](https://developer.apple.com/documentation/realitykit/loading-entities-from-a-file), [CPU and asset performance](https://developer.apple.com/documentation/realitykit/reducing-cpu-utilization-in-your-realitykit-app).

OpenUSD supports deferred payload composition and an efficient model hierarchy for discovering important assemblies. That is useful during processing, but a USD payload declaration does not prove that RealityKit exposes the same runtime load/unload controls. Use explicit approved native packages until the selected API demonstrates selective loading. [OpenUSD load/unload and model hierarchy](https://openusd.org/release/glossary.html#usdglossary-loadunload).

The recorded native samples are **macOS preparation/installation measurements**, not iPhone FPS: raw source 25.79 MB / 2.99 million expanded triangles, with 4.126 seconds preparation in one sample. The conservative derivative is 10.55 MB and the distance derivative 9.33 MB. Source identity, hierarchy and processing checks are recorded in [native import evidence](evidence/imported-rack-native.json) and [mobile derivative validation](evidence/mobile-rack-validation.json). Measure physical iPhone and iPad peak footprint, first visible frame, insertion hitch, draw calls and steady frame time before calling any profile optimized for those devices. See the separate [Apple import API reference](realitykit-import-references.md).

## Documentation and code readability

Keep `SpatialCore` as the accepted-data boundary and `SpatialApple` as its native projection. Keep content-specific names, part bindings and teaching metadata in `assets/imported-rack`; keep tool aliases and compact context in `backend/src/astra`. An asset-detail coordinator should orchestrate existing preparation and scene edits, not introduce another scene store or reducer. A public SDK package is unnecessary to prove these boundaries; the existing second generated example is the useful generality test.
