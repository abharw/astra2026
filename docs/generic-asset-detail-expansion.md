# Generic asset detail expansion

The model receives two distinct views: the complete accepted scene and a bounded list of available detail templates. The first describes what is installed. The second describes host-approved children that could replace an opaque exterior on specific currently intact instances. Names and roles are asset data; the framework has no fixed rack, server or processor levels.

`phone.snapshot.availableAssetDetails` is optional. An entry has a stable `detailId`, eligible `targetNodeIds`, `name`, optional `description`, content-addressed `assetID`, `byteCount`, `triangleCount`, and immediate `children`. Each child supplies `partID`, local `transform`, `semantic` and `provenance`. The native catalog supplies these fields; the model cannot choose an arbitrary URL, resource hash, source transform or provenance. Availability is captured at request admission alongside the scene revision and intent epoch, and an omitted catalog clears previous availability.

After every eligible instance has expanded, the host retains the template with `targetNodeIds: []` while accepted scene nodes still use its imported resource. It provides source structure and exact parent-local rest transforms for explanation and reassembly, and authorizes no additional expansion. These source poses remain distinct from current poses in the accepted scene. The model matches observed geometry resource and part IDs to the template to restore children while retaining their assembly parent's current pose. Unreferenced geometry definitions alone do not keep this context alive.

The model can propose `{ "kind": "expandDetail", "nodeRef": "observed-instance-id", "detailId": "advertised-template-id" }` in patch mode. The backend expands this into existing portable operations: clear the target's geometry and material, put immutable imported geometry definitions, and create its immediate child nodes. It retains the target ID, parent edge, current translation, rotation, scale and visibility, plus any existing children. It never changes other instances automatically. Repeated instances reuse geometry definitions; their child IDs are deterministic hashes of target ID, detail ID and part ID.

The native client prepares approved resources before its existing atomic validation/reducer/install path. Narration still waits for the installation receipt. A model-authored explanation cannot establish that a resource loaded successfully or is inside the camera view. A future snapshot exposes installed child IDs for subsequent movement, explanation or another advertised expansion. Each template covers one arbitrary hierarchy edge; deeper content can be represented by further matching templates without adding domain-specific operations.

The host calls `SceneController.registerAssetDetails(_:resources:cacheDirectory:)` with Codable `ImportedAssetDetailTemplate` values and `ImportedAssetDescriptor` resources. Registration checks exact part approval, immutable identities, finite local poses and bounded metadata without opening a file. Each template supplies exact `matches` of source asset/part IDs; application data owns those bindings. The renderer lazily prepares a referenced approved package during the existing patch transaction. It leases resources through preparation, rechecks scene ID, session, revision, intent epoch and active execution identity, then commits synchronously. A stopped or superseded load cannot install late children; a failed digest or missing resource leaves the overview and Undo state intact.

Semantic expansion replaces only the selected node's render geometry, keeping it as the assembly parent. Consequently, the authored child transforms must be expressed in that parent's existing coordinates. For the example server's imported Z-up wrapper, source-local rest transforms already match; applying another source-to-RealityKit rotation would rotate the content twice. This coordinate rule is a host asset binding, not inference performed by the model.

The authoring policy chooses the smallest useful level. Moving an assembly requires `translate`, which preserves its internal structure. A detailed explanation may expand one relevant instance. Asking for “one” or “an example” permits choosing a representative; “this” or “that” needs selection or a resolvable recent referent. Missing source detail remains missing: the model may explain that limitation or generate geometry marked illustrative.

Admission bounds are 32 templates, 128 eligible targets per template, 32 immediate children per template and 128 KiB of serialized availability. Each approved resource is bounded by 128 MiB and two million claimed triangles. IDs, descriptions, references, finite transforms and unit quaternions are validated. Every normalized patch must fit 128 operations after expansion and shared-geometry factoring; excess work is rejected before device delivery. Existing-ID collisions and repeated or unadvertised expansion are also rejected. Native content verification and resource limits remain authoritative over host metadata.

Verification uses unrelated optical and lamp fixtures. Backend tests prove preservation of moved/rotated/scaled parents and existing child edges, isolation of the other instance, shared immutable geometry, deterministic IDs, explicit geometry/material clearing, collision and repeat rejection, wire-operation bounds, scoped availability and receipt-gated narration. Parser tests cover the Unicode byte budget, all nested unknown fields and legacy snapshots. The native integration has separate tests for resource preparation and atomic installation; see their current results before treating a device demo as accepted.

The eight normal native detail tests load small bundled synthetic lamp packages and cover successful expansion, subsequent child movement, two-step Undo, immutable/lazy registration, unapproved or corrupted resources, retained source poses after the last instance expands, and stopping during asynchronous preparation. A held local HTTP response proves cancellation releases the ordered receive loop for a following scene message. A three-package regression proves cached candidate resources stay leased while another package loads. An opt-in exact app fixture test (`ASTRA_TEST_DETAIL_APP_ROOT=/path/to/astra2026 swift test --package-path packages/SpatialKit --filter approvedAppDetail`) verifies 20→29 nodes when one of 18 source instances expands into its nine authored groups, preserving the other instances and the selected current pose. These are macOS RealityKit controller checks, not physical AR frame-rate or hand-selection acceptance.
